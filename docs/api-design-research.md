# WhyNoIPv6 API Redesign — Design Report

**Status:** research/design round — proposes the post-compat API; not yet folded into docs/spec.
Maintainer decisions applied 2026-07-09 (see §11 Resolved): no URL version segment; short tier
collection paths; `meta.stability` removed; history import deferred (start fresh); tld + provider
pivots added; mandate-tracking accepted.

**Date:** 2026-07-07. Clean-slate API design after the frozen-frontend constraint was
dropped. Input: the data-surface / feature-surface / compat-cruft spec review, the
REST-conventions / pagination-scale / errors-caching-negotiation / comparable-apis /
tooling-artifacts web research, plus study of the existing `docs/spec/07-api.md` (to be
rewritten from this report), `05-schema.md`, `03-state-machine.md`, and
`docs/backend-design.md` (house style).
**Convention:** every major decision states its rejected alternative(s). Open items are
marked **OPEN-n** and gathered in §11.
**Scope note:** this report covers *only how confirmed data is exposed*. The data model
(05-schema.md) and the confirmed-state trust machine (03-state-machine.md) are unchanged;
the crawler/engine (backend-design.md §2) is unchanged. What changes is the wire.

## 1. Executive summary

The new API is a **read-only, anonymous, unversioned JSON API at the root of
`api.whynoipv6.com`** (no URL version segment) that serves the *real* WhyNoIPv6 data model — the 4-valued confirmed
`ipv6_status` per dimension, the `classification` enum, the `class_flags[]` array, the
`gold` boolean, and the `*_since` provenance timestamps — **directly, with no projection, no
message rendering, and no legacy compatibility layer**. Every list is a
**keyset/cursor-paginated collection** over an object envelope; every error is **RFC 9457
`application/problem+json`**; the whole surface is **OpenAPI-3.0.3-first**, with Go server
types generated by oapi-codegen (chi + strict-server) and TypeScript types generated by
openapi-typescript from the same committed `openapi.yaml`.

The eight headline decisions:

1. **`api.whynoipv6.com/` with no URL version segment.** The `api.` subdomain carries the
   "api" role; resources sit at the root (no `/v1`, no doubled `/api/v1`). The API is
   frontend-facing with no external consumers today, so versioning for outside users is
   speculative; if third-party consumers ever appear, a version segment or header can be
   introduced then (additive). Reject Zalando-style media-type versioning (over-engineered
   for a single first-party consumer) and premature URL-path `/v1` versioning (buys nothing
   for a no-consumer API).
2. **Plural, verb-free, self-describing resource paths keyed by natural id.** `/domains/{host}`,
   `/countries/{code}`, `/asns/{number}`, `/campaigns/{uuid}`, `/changelog`. The legacy
   `/metric` singular, `/domain`-means-sinner, shortuuid tokens, and `{"data":[…]}`
   envelope are all deleted.
3. **`snake_case` on the wire, one consistent envelope.** Symmetry with the entire
   Postgres → sqlc → Go → OpenAPI stack, which is already snake_case. Collections return
   `{ "items": [...], "page": {...}, "meta": {...} }`; time-series return
   `{ "points": [...], "meta": {...} }`; single resources return the object with a sibling
   `meta`. Never a bare array.
4. **Keyset/cursor pagination on every large collection.** Opaque base64url cursor over a
   strict total order (`(rank, id)` on rank-sorted views, `host` on curated sets, a
   null-flag-first key on the nullable-rank dependents list), plus an `after_rank`
   deep-link escape hatch on the rank-ordered views only. No exact `COUNT(*)` on the hot
   path; `max(rank)` is the O(1) headline total, exact counts survive only on the genuinely
   bounded curated sets. This replaces the removed offset-50 scheme.
5. **The confirmed model is the wire model.** Per-dimension `{base,www,ns,mx,conn,resources}`
   status objects carry the 4-value enum + JSON `null` (never confirmed), plus `since`.
   `classification`, `class_flags[]`, `gold` are first-class. The `legacyStatus`
   3-string projection, the `renderChangelog` ladder, and the reverse message-map are
   deleted outright. Raw observation values (`error`/`inconsistent`) never reach the wire
   except inside the optional `evidence` block.
6. **RFC 9457 errors + RFC-correct HTTP.** GET/HEAD/OPTIONS for the read surface; the only
   write is `POST /check` (the async live check). `/livez` + `/readyz` live at the root and
   outside the public OpenAPI. One small fixed set of `problem` type URIs.
7. **Cache-first, CDN-absorbed reads; rate-limit only the write.** Daily-batch data is
   ideal for shared caching: `Cache-Control: public` with `s-maxage` tied to crawl
   cadence, an ETag derived from the crawl generation, `304` on conditional GET, gzip +
   Brotli at the edge. `POST /check` is `no-store` and per-IP (and per-IPv6-/64)
   rate-limited with `429` + `Retry-After` + `RateLimit` structured-field headers.
8. **Genuinely-different representations get their own URLs.** SVG badge at
   `/badge/{host}.svg` (+ a shields.io endpoint-JSON variant), Atom/JSON-Feed change feeds
   per scope, CSV via `?format=csv`, and bulk datasets served *statically by nginx* under
   `/datasets/` with a `datapackage.json` manifest, SHA-256 checksums, a stable `latest/`
   alias, and an optional Zenodo DOI. The API itself only serves the manifest.

Plus one resolved decision (§9, OPEN-9, 2026-07-09): **start fresh — no history import for
now** (revisit later). The DNS-flip cutover carries **no data import** at all: both the
`changelog` and the `scan` hypertable begin empty, and the changelog-sourced features (diff /
change-feeds / per-domain history / "State of IPv6") fill over the months following launch.
This drops the `legacy_*` changelog columns unconditionally and collapses the cutover to a
pure DNS flip.

## 2. Design principles

### 2.1 Still locked (the API must honor these)

- **Public and anonymous.** No accounts, auth, API keys, billing, per-user state. The only
  client-identifying signal is IP (for rate-limiting the one write endpoint) and an
  optional courtesy `User-Agent`/`?sourceapp=`.
- **The status model is fixed:** 4-valued confirmed `ipv6_status`
  (`supported`/`unsupported`/`no_record`/`not_applicable`) plus JSON `null` for
  never-confirmed; the deterministic `classification` ladder
  (`hero`/`partial`/`sinner`/`inactive`/`unknown`) with a `gold` tier and `class_flags[]`
  reason flags. **No letter grades, no 0–100 scores.** Aggregate adoption *percentages*
  (country/campaign/ASN) are allowed — they are aggregate stats, not per-entity scores.
- **Data source:** Tranco top-1M, eTLD+1, plus community campaign lists. Non-commercial;
  the license is stated in-band (§6.3).
- **Stack:** current Go, Postgres 18 + TimescaleDB, pgx/v5, chi v5, sqlc, slog,
  OpenAPI-first.

### 2.2 Freedoms unlocked by dropping compat

The old spec froze 25 "legacy (L)" endpoint shapes byte-for-byte so an unchanged Vue
frontend kept working. That frontend is being rebuilt (keeping only its visual design),
the cutover is a DNS flip, and there are **no API consumers today**. Therefore:

- We design **one** clean resource set, not L + N duplicated surfaces.
- We serve the **real** enum, not the 3-string projection.
- We choose pagination, envelope, naming, and error shape from scratch.
- The one-time production **data migration is no longer required** — a fresh crawl is
  acceptable, so the parity gates, byte-equality changelog transform, and reverse
  message-map are obsolete (a best-effort structured history import remains optional, §9).

The guiding stance, borrowed from the comparable no-auth measurement APIs (RIPEstat,
Cloudflare Radar, Internet Society Pulse, internet.nl): **lean on heavy caching + a CDN,
version conservatively, signal freshness and stability in-band, and keep bulk consumers
off the pagination path via a separate static download channel.**

## 3. Core conventions

### 3.1 Base URL + versioning

**Decision: no URL version segment.** All data endpoints sit at the **root of
`api.whynoipv6.com`** — the `api.` subdomain already names the role, so there is **no `/v1`**
and no doubled `/api/v1`. Real URLs are `https://api.whynoipv6.com/domains/{host}`. The API is
frontend-facing with **no external / third-party consumers today**; versioning for outside
users is therefore speculative machinery. Changes stay additive by discipline (new fields,
new endpoints, new optional query params); a breaking change is a project decision, not a URL
concern. If third-party consumers ever appear, a version segment or an `Accept`-header version
can be introduced then — that is an additive move, cheap to make later and not worth paying
for now. Operational endpoints (`/livez`, `/readyz`) were already outside any version segment
and stay at the **root**, unchanged; the static `/datasets/` tree likewise lives at the root
and outside the public OpenAPI document.

*Rejected — URL-path `/v1` versioning.* Premature for a no-consumer API: a `/v1` prefix is
baked into every URL and the OpenAPI `servers` block for the benefit of external consumers
who do not exist. Reintroducing a version segment later (if outside users appear) is an
additive change, so nothing is lost by omitting it now. (The doubled `api.whynoipv6.com/api/v1`
form was doubly rejected — the `api.` subdomain and an `/api/` path prefix are redundant.)
*Rejected — media-type / `Accept`-header versioning (Zalando Rule 115, GitHub).* Optimized
for a large internal microservice mesh with many independent consumer teams. Here there is
one first-party consumer and a public read API; header versioning is harder to test, less
discoverable, uncacheable-by-URL, and buys nothing today. If a versioning need ever arrives,
an `Accept`-header version is one of the additive options on the table.

### 3.2 Resource naming

**Decision.** Lowercase **plural** collection nouns, **verb-free**, hierarchy as
`/collection/{id}/sub-collection`, kebab-case for any multi-word segment. Item access by
**stable natural id**:

| Resource | Collection | Item | Natural id |
|---|---|---|---|
| Domain | `/domains` | `/domains/{host}` | `host` (lowercase punycode FQDN) |
| Country | `/countries` | `/countries/{code}` | ISO-ish `CHAR(2)`, `UN` sentinel |
| ASN / provider | `/asns` | `/asns/{number}` | `BIGINT` AS number, `0`=Unknown |
| Campaign | `/campaigns` | `/campaigns/{uuid}` | raw canonical UUID |
| Resource host | `/resources` | `/resources/{host}` | canonicalized host |
| Changelog | `/changelog` | — (feed; addressed by scope + cursor) | — |

Sub-collections: `/countries/{code}/domains`, `/asns/{number}/domains`,
`/campaigns/{uuid}/domains`, `/domains/{host}/subdomains`, `/domains/{host}/resources`,
`/resources/{host}/dependents`, `/domains/{host}/changelog`, `/domains/{host}/history`.

The classification tiers are promoted to their own **short, canonical plural collection
paths** — the browse URLs the frontend links to:

| Tier collection | Preset over `/domains` |
|---|---|
| `/heroes` | `class=hero` |
| `/sinners` | `class=sinner` |
| `/gold` | `gold=true` |
| `/almost` | the "almost there" list (partial domains one step from hero) |
| `/mail` | the mail/MX heroes track |

Each is a **preset filtered view over the domain leaderboard**, sharing the exact same
keyset/cursor pagination, §5.2 row shape, and `?country=`/`?asn=` filter composition as
`/domains`. They accept the same additional filters, so "sinners in Norway" is
`GET /sinners?country=no`. `GET /domains` remains the **general filterable collection** whose
`?class=` param spans every tier (`class=partial`, etc.); the tier paths are short aliases
over it, not a second vocabulary.

**Host as a path key.** The eTLD+1 `host` is stable, unique, SEO/deep-link friendly, and
already the schema's `UNIQUE` natural id. Canonical form (from the engine's `Canonicalize`):
lowercase, A-label (punycode) for IDNs, no trailing dot, ≥2 labels. The API canonicalizes
the path parameter before lookup; a value that fails canonicalization is a `404`
(exception: the badge endpoint returns `400`, §6.2, because a malformed embed is not a
legitimate request). This replaces shortuuid URLs entirely; synthetic `domain.id` is
internal-only and never appears on the wire except inside opaque cursors.

*Rejected — keep `/metric` (singular) and `/domain`-means-sinner (`?domain=sinner`).* Path
names that encode hidden meaning are a legacy accident; self-describing plural nouns are the
AIP/Microsoft/Zalando consensus. Note this is **not** the same as the dedicated plural tier
collections (`/heroes`, `/sinners`, `/gold`, `/almost`, `/mail`): those are transparent short
aliases over the filterable `/domains` collection (a `/sinners` path is self-describing,
whereas `/domain`-means-sinner hides meaning) and are used deliberately.
*Rejected — shortuuid campaign tokens.* Their sole justification was preserving
previously-shared `/campaign/{22-char}` links across the migration; moot under a DNS flip
with a rebuilt frontend and no consumers. Serve the raw UUID (OPEN-1: an optional human
`slug` column is a later nicety).
*Rejected — synthetic ids in URLs.* The natural ids are stable and human-meaningful;
exposing `domain.id`/`campaign.id` would be a gratuitous indirection.

### 3.3 Field naming — `snake_case`

**Decision.** Emit **`snake_case`** field names on the wire, uniformly, everywhere.

This is a deliberate, close call. The web research correctly notes camelCase is the
mainstream default for TS-facing APIs (~71%). But the deciding factors here pull the other
way:

- The **entire existing surface is snake_case**: the schema, the sqlc-generated Go
  structs, `03/05` vocabulary, and the already-designed `§4` "new" endpoints
  (`class_flags`, `country_code`, `as_of`, `last_checked_at`). Flipping to camelCase means
  re-tagging ~60 domain fields and diverging the wire from every other spec document.
- **OpenAPI-first neutralizes the frontend argument.** openapi-typescript generates typed
  TS bindings from whatever case the spec declares; the rebuilt frontend is transform-free
  either way. snake_case TS property names are non-idiomatic but fully type-safe.
- **Near-zero mapping layer.** sqlc row structs serialize essentially straight to the wire
  with no per-field `json:"camelCase"` divergence and no DTO-mapping step — the house
  preference for symmetry with the Postgres/Go layer (Zalando Rule 118 endorses this).

The one hard rule everyone agrees on is honored: **never mix cases within a response.**

**Two explicit, bounded exceptions to "no mapping / never mix," both lint-enforced:**

- **snake_case normalization of smushed column names.** A handful of schema columns are
  written without a separator (`country.v6sites`); these are normalized to canonical
  snake_case on the wire (`v6_sites`). This is a mechanical, total, lint-checked
  case-normalization — not a semantic DTO remap — so the "no mapping layer" rationale still
  holds. Where the same concept has two schema spellings (ASN `count_v6` in the `asn` table
  vs `v6_domains` in `stats_asn_daily`), the API picks **one** wire spelling and uses it in
  both the detail and time-series representations (see §5.6/§5.10).
- **The shields.io badge JSON (§6.2)** emits camelCase (`schemaVersion`, `cacheSeconds`,
  `isError`) because its field names are dictated by shields.io's external endpoint schema,
  not ours. It is a deliberate exception to the snake_case rule; the API's *own* surface
  stays snake_case throughout.

*Rejected — camelCase.* More idiomatic for the TS frontend, and defensible; but it forces
a json-tag mapping layer across the whole domain model and diverges from the rest of the
spec, to benefit a consumer that is type-generated from the contract anyway. If a future
maintainer weights frontend idiom over stack symmetry, this is the reversible decision to
revisit — but it must be decided once and linted so it never drifts.

### 3.4 Envelope + list-response shape

**Decision.** A **thin, ad-hoc envelope**, not full JSON:API. There are exactly **two**
collection shapes, both documented here so the generated envelope type is uniform:

**A. Item collections** (leaderboards, sub-collections, feeds) return a top-level object,
never a bare array:

```json
{
  "items": [ /* resource objects */ ],
  "page": {
    "next_cursor": "cD1yYW5rOjEwMDI...",
    "prev_cursor": null,
    "has_more": true
  },
  "meta": {
    "as_of": "2026-07-07T03:41:12Z",
    "generation": 20260707,
    "count_estimate": 1003418,
    "license": "CC-BY-NC-4.0"
  }
}
```

**B. Time-series collections** (`/stats/*`, `/domains/{host}/history`, campaign/country/asn
`/stats`) use **`points`** as the collection key instead of `items`, and carry **no `page`**
(they are bounded by the date window, never cursor-paged):

```json
{ "points": [ /* time-ordered rows */ ], "meta": { "as_of": "...", "source": "confirmed_state" } }
```

`points` is the **only** sanctioned alternate collection key; it is declared here so a typed
client models exactly two collection variants (`items`+`page` vs `points`). Everything else
about the envelope is identical.

**Single resources** return the resource object with a sibling `meta`:

```json
{ "host": "example.com", "...": "...", "meta": { "as_of": "..." } }
```

**Uniform rules across every collection:**

- **`page` is always the same shape** — `{ next_cursor, prev_cursor, has_more }` — and
  `prev_cursor` is **always present** (`null` when there is no previous page). Bounded
  non-paged item collections (campaign members, `/shame`, forward-resources) still emit a
  `page` with all three fields (`has_more: false`, cursors `null`) so the type never varies.
- **Counts live only in `meta`, never as an `items`-sibling.** A collection carries *either*
  `meta.count_estimate` (approximate — the default for anything derived from a large or
  filtered `domain` scan) *or* `meta.count` (exact — only the genuinely bounded curated
  sets: campaign members, `/shame`, forward-resources). A client reads count from `meta`,
  full stop.
- **`meta` is deliberately thin** (RIPEstat/Radar precedent): `as_of` (freshness signal),
  `generation` (integer crawl id, the ETag/cache-key seed), `count`/`count_estimate` where
  applicable, `license`. Never nest `items`/`data`/`points` more than one level. (No
  per-response `stability` marker: with no external API consumers and no URL versioning, a
  `stable`/`beta`/`deprecated` flag is speculative machinery that only adds noise — it can be
  added later if the API gains third-party users.)

**`generation` and `as_of` sources (they seed the ETag/cache story, §7.1, so they must be
deterministic across backend instances).** `generation` is the integer `YYYYMMDD` derived
from **`max(stats_global_daily.day)`** — an O(1) lookup, monotonic, identical on every
instance, and requiring **no schema change**. `as_of` is the crawl-rollup completion
timestamp; the cleanest source is a single `generated_at TIMESTAMPTZ` recorded by the daily
stats rollup (a one-column addition, flagged in §10.3). Until that column exists, `as_of`
falls back deterministically to `max(stats_global_daily.day)` at `00:00:00Z`. The
per-worker `crawler_metrics.run_id` UUID is **not** used — it is neither monotonic nor
per-crawl.

*Rejected — full JSON:API (`type`/`id`/`relationships`/`included` sideloading).* Pays off
only for graph-heavy relational data with N+1 fetch problems. The whynoipv6 graph is
shallow (domain → country/asn/status); embed the few related fields directly (`country`,
`asn` objects on the row) or expose sub-collection endpoints. JSON:API here is pure
ceremony.
*Rejected — bare top-level arrays.* Force metadata (pagination, freshness) into HTTP
headers and produce a shape you can't extend without breaking clients (Zalando Rule 110).
*Rejected — the legacy `{"data":[…]}` search envelope.* One-off inconsistency; deleted in
favor of the single `{items,page,meta}` / `{points,meta}` shapes used by *every* collection.

### 3.5 Error format — RFC 9457

**Decision.** Every 4xx/5xx is **`application/problem+json`** per RFC 9457 (the current
IETF standard, obsoletes 7807):

```http
HTTP/1.1 404 Not Found
Content-Type: application/problem+json

{
  "type": "https://whynoipv6.com/problems/domain-not-found",
  "title": "Domain not found",
  "status": 404,
  "detail": "No crawl record for example.invalid.",
  "instance": "/domains/example.invalid"
}
```

The `status` member must equal the HTTP status line (RFC 9457 requirement) so dumb
intermediaries/CDN behave. `type` URIs are stable and resolvable on the site (they double
as documentation). The fixed set — small, because there are no accounts:

| `type` (relative to `/problems/`) | HTTP | When |
|---|---|---|
| `not-found` | 404 | unknown/uncanonicalizable domain, country, asn, campaign, resource |
| `invalid-parameter` | 400 | malformed cursor, bad `format`, malformed host on badge |
| `validation-error` | 422 | out-of-range/invalid enum filter value (a value not in the enum); adds `errors:[{field,reason}]` |
| `scope-required` | 422 | a *valid* filter value that needs a companion scope to stay indexed (bare `?flag=`, bare per-dimension `?mx=`); `detail` names the scope params that satisfy it |
| `rate-limited` | 429 | `POST /check` over quota; adds `retry_after` + `Retry-After` header |
| `not-acceptable` | 406 | `Accept` cannot be satisfied on a JSON endpoint |
| `unsupported-media-type` | 415 | `POST /check` body not JSON |
| `manifest-unavailable` | 503 | `/datasets` manifest missing/unparseable (the only 503) |
| `internal-error` | 500 | unexpected fault; `detail` is generic, never a stack trace |

Note the deliberate split between `validation-error` (your *value* is invalid — not a member
of the enum) and `scope-required` (your value is perfectly valid but, for performance, needs
an indexed companion scope, §4.3). Conflating the two misleads clients.

*Rejected — a bespoke `{"error":"not_found"}` envelope.* That is precisely the kind of
one-off contract being dropped; the legacy byte-exact, capitalization-divergent error
strings (`"no domains found"` vs `"No domains found"`) are deleted. RFC 9457 gives the TS
frontend one predictable, OpenAPI-documentable error contract, and Zalando/Spring/ASP.NET
all default to it.

### 3.6 HTTP semantics

**Decision.** The read surface is **GET** (with implicit HEAD/OPTIONS). The *only* mutating
verb in the whole API is **`POST /check`** (enqueue a live check, §6.1) — an
explicitly-modelled async job, not a resource mutation. No PUT/PATCH/DELETE anywhere; no
CSRF surface on reads.

Status codes: `200` with the resource; `404` for an unknown entity; `400` for a malformed
request/cursor/filter; `422` for a semantically-invalid enum value or a scope-required
filter; `406`/`415` for negotiation failures; `429` for rate-limit; `304` on a
conditional-GET cache hit; `202` on `POST /check` enqueue; `5xx` for faults. **Never** a
`200`-with-error-body — the status code always carries the outcome. **No HATEOAS** (REST
maturity level 2): the single first-party client hard-codes its routes; the OpenAPI document
is the discoverability substitute.

**Zero-result is `200`, not `404`.** A search with no matches, a filter that selects
nothing, and paging past the end all return `200` with an empty `items` array — the legacy
"bug-compatible 404 on zero results / page-past-end / by-domain changelog" behavior is
deleted. A `404` is reserved for *the addressed entity does not exist* (unknown host/code/
asn/uuid).

### 3.7 Health endpoints

**Decision.** The Kubernetes/Google z-page split, at the **root** (they were already outside
any version segment):

- **`GET /livez`** — `200` whenever the process is running; no dependency checks. A failure
  means *restart me*.
- **`GET /readyz`** — `200` only when Postgres/TimescaleDB is reachable and the app can
  serve; a failure means *stop routing traffic without restarting*. Optional JSON body
  listing individual checks, but orchestration is driven off the status code.

Both are excluded from the public OpenAPI, from CDN caching (`Cache-Control: no-store`),
and from rate-limiting.

*Rejected — a single `/healthz`.* Deprecated in favor of the liveness/readiness split; one
endpoint can't distinguish "restart me" from "don't route to me," which is the entire point.

## 4. Pagination, filtering, sorting

This section is load-bearing: the master list is the Tranco top-1M ranked by rank, and the
legacy offset-50 scheme is deleted.

### 4.1 The decision: keyset/cursor, not offset

**Decision.** **Keyset (seek-method) pagination** is the primary access pattern for *every*
collection large enough to page — `/domains`, its country/asn-scoped variants, the reverse
`dependents` list, and campaign members. **Offset pagination is not used anywhere.** Exact
`COUNT(*)` survives only on the genuinely-bounded curated sets (campaign members, `/shame`,
forward-resources), where the row count is a few tens and exact is trivially cheap.

**Why the country/asn-scoped lists are *not* "small bounded" and must use keyset too.**
Tranco's top-1M is heavily concentrated: a single large country (US, CN, DE) or a hyperscaler
ASN (Cloudflare/Amazon/Google/Fastly host huge numbers of eTLD+1s) can hold tens to hundreds
of thousands of domains. On those scopes, offset deep-pages walk-and-discard exactly like the
global 1M list and an exact `COUNT(*)` is exactly the per-request full scan we are avoiding.
So `/countries/{code}/domains` and `/asns/{number}/domains` reuse the **rank keyset**
(`(rank, id)`), which composes cleanly with rank order via `idx_domain_country` /
`idx_domain_asn` plus the `(rank, id)` tiebreaker, and report an **estimated**
`count_estimate` — never an exact count. The one truly-small curated set is **campaign
members** (a hand-curated list, typically tens of rows); those still get an exact
`meta.count`, but paged with the same cursor page type for envelope uniformity.

Why keyset for the large lists, from the research:

- **Offset degrades linearly with depth.** Postgres walks and discards every skipped row
  before returning the page; deep pages on a large leaderboard are the pathological case
  (Slack abandoned offset for exactly this). Keyset uses a `WHERE key > :last` seek on an
  index — **constant cost regardless of depth**.
- **Offset is incorrect on a mutating set.** The daily crawl re-ranks; between two page
  loads offset silently skips/duplicates rows. Keyset over a stable key does not shift.
- **Rank is the ideal keyset key** on rank-ordered views. It is monotonic, indexable
  (`idx_domain_rank`), and human-meaningful, which uniquely lets us keep offset's only real
  advantage — random page jumps — as an indexed range scan (`WHERE rank > :n`) with none of
  offset's row-walking cost (§4.2).

**Default `/domains` scope.** The bare top-level `/domains` collection is **ranked,
non-disabled rows only** (`WHERE rank IS NOT NULL AND NOT disabled`). Rank-NULL entities
(campaign-only hosts, subdomains, live-check hosts) are real `domain` rows but are reachable
**only via their sub-collections** (`/campaigns/{uuid}/domains`, `/domains/{host}/subdomains`,
`/resources/{host}/dependents`), never from the top-level leaderboard. This keeps the keyset
seed total (§4.2). `meta.count_estimate = max(rank)` is an **upper bound** — disabled ranked
rows retain their rank but are filtered out, so the true count is slightly lower; it is
labelled an estimate for exactly this reason.

### 4.2 Cursor design

The cursor is an **opaque base64url token**. Even though the underlying key is often public
rank, opacity lets the server evolve the scheme and validate staleness. It encodes:

```
{
  "v": 1,                    // cursor schema version
  "g": 20260707,             // crawl generation the cursor was minted against
  "s": "rank",               // sort key
  "f": "a3f9c1",             // filter fingerprint (hash of the normalized filter set)
  "k": [10023, 88142]        // the seek tuple (shape depends on the sort key)
}
```

Each sort binds a **strict total order** and its own seek tuple:

- **`rank` (default, and country/asn scopes):** `(rank, id)` with `id` as the
  guaranteed-unique tiebreaker (Tranco rank can tie or shift). Qualified `rank IS NOT NULL`,
  so the seek tuple is always total — NULL ranks are excluded from this ordering by the
  scope predicate (§4.1), which is why the row-value comparison is well-defined.

```sql
SELECT ... FROM domain
WHERE classification = 'hero' AND rank IS NOT NULL AND NOT disabled
  AND (rank, id) > ($1, $2)          -- seek tuple from the cursor
ORDER BY rank, id
LIMIT $3 + 1;                        -- N+1 fetch → compute has_more, drop the extra
```

- **`host` (campaign members, and the `sort=host` option):** `host` alone is a unique
  natural id, so `host > $1` is already a strict total order — no tiebreaker, no NULL. This
  is the ordering used for campaign members, whose `rank` is usually NULL.
- **Nullable-rank ordering (`dependents`, §5.11):** the reverse `dependents` set mixes
  ranked and rank-NULL rows and is ordered `rank NULLS LAST`. A plain `(rank, id) > (…)`
  comparison evaluates to `UNKNOWN` on NULL rank and would silently drop the entire
  null-rank tail. So `dependents` uses a **null-flag-first** key that makes the flag the
  primary sort column:

```sql
SELECT ... FROM domain
WHERE ... AND (rank IS NULL, rank, id) > ($1, $2, $3)
ORDER BY (rank IS NULL), rank, id
LIMIT $4 + 1;
```

  The cursor's seek tuple is then `[is_rank_null, last_rank, last_id]`. The
  `rank IS NOT NULL` global-list seek is **never** reused verbatim for this nullable ordering.

**Staleness handling.** A cursor whose `g` (generation) differs from the current crawl
generation is *re-anchored*: because rank is monotonic, the server seeks to the same
`last_rank` in the current generation and continues — a domain's rank barely moves
day-to-day, so continuity is preserved. If the filter fingerprint `f` no longer matches the
request's filters, the cursor is rejected with `400 invalid-parameter` (the cursor is only
valid for the sort+filter it was minted under). Bidirectional paging (`prev_cursor`) is
supported for scroll-both-ways leaderboard UX.

**Deep-link escape hatch — rank-ordered views only.** Alongside the opaque cursor,
`?after_rank=500000` (and `?around_rank=500000` for a centered window) provide shareable,
stateless deep links — `WHERE rank > 500000 ORDER BY rank LIMIT n`, an indexed range scan.
**Scope of the claim (honest):** `after_rank`/`around_rank` are supported **only on the
rank-ordered views** and mean *"rows whose global rank ≥ N, then filtered"* — **not** "the
Nth matching row." On a sparse filter (`class=hero` selects ~41k of 1M), ranks are
sparse within the filter, so `after_rank=N` returns "heroes whose global rank > N," which is
not "page N of heroes." The `sort=host` ordering has **no** random-access param — it is
forward/back cursor only. If the frontend genuinely needs "page N of heroes," that requires a
precomputed **dense per-filter rank**, flagged as **OPEN-14**, not something `after_rank`
provides.

`?limit` is client-supplied with a sane cap (`default 50`, `max 200`).

### 4.3 Filter / sort / field-selection grammar

Filters are plain query params (Radar precedent), aligned with response field names, and
**constrained to the indexed axes** — the review is explicit about which predicates are
cheap:

| Param | Values | Backed by | Notes |
|---|---|---|---|
| `class` | `hero`\|`partial`\|`sinner`\|`inactive`\|`unknown` | `idx_domain_heroes/sinners/partial` | primary filter (the shortened general param; presets the `/heroes`,`/sinners`,`/gold`,`/almost`,`/mail` tier paths); predicate spelled `AND rank IS NOT NULL AND NOT disabled` so the partial index is used |
| `gold` | `true` | layered on `idx_domain_heroes` | gold ⊂ hero, cheap without its own index; the `/gold` tier path |
| `country` | ISO code | `idx_domain_country` | composes with `class` + rank order |
| `asn` | AS number | `idx_domain_asn` | equality cheap; sort within pays a sort |
| `flag` | one of `class_flags` | **expensive** — scope-required (see below) | |
| `base`/`www`/`ns`/`mx`/`conn`/`resources` | a `ipv6_status` value | **expensive** — scope-required (see below) | per-dimension confirmed-status filters (drives the mail track) |
| `rank_max` / `rank_min` | int | `idx_domain_rank` | cohort ranges (top-1000 etc.) |
| `q` | substring | `idx_domain_host_trgm` | search; **does not** compose with rank ordering — returns host/relevance-ordered, its own path |
| `sort` | `rank` (default) \| `-rank` \| `host` | index-dependent | each sort binds a distinct cursor ordering (§4.2) |
| `fields` | comma list | — | sparse fieldset to trim the leaderboard row |
| `format` | `json` (default) \| `csv` | — | content negotiation (§6.5) |

**Guardrails against expensive predicates (from the review).**

- **`flag=` and the per-dimension status filters (`mx=supported`, `base=unsupported`, …) are
  the same class of unindexed predicate** — there is no `class_flags` GIN index and no
  `*_status` index, so a bare `?flag=broken_v6` or `?mx=unsupported` over all 1M rows is a
  seq scan. **Rule (scope-required):** these filters are accepted **only** when combined with
  an indexed prefilter (`class`, `country`, or `asn`). A bare, unscoped one returns
  **`422 scope-required`** (§3.5) — *not* `validation-error`; the value is valid, it just
  needs a scope — with a `detail` naming the scope params that satisfy it. (OPEN-2 would add
  a `class_flags` GIN index to relax the `flag=` half of this rule.)
- **The global mail-heroes / mail-sinners lists are served from stats, not a live scan.** A
  site-wide "all domains missing IPv6 mail" list (`mx=unsupported`, equivalently
  `flag=mail_missing`) is precisely the unscoped seq-scan case above. The **aggregate
  headline numbers** come from the daily `*_supported` stats counters; the **list form** is
  offered only as a `class`/`country`/`asn`-scoped filtered `/domains` view (§5.4).
- **Arbitrary cross-dimension boolean predicates** (`base=supported AND mx=unsupported` with
  no scope) are not offered — no composite index covers them. The public filter surface is
  the indexed axes plus the cheap layered booleans (`gold`) plus the scope-required
  per-dimension/flag filters.
- **No request-time aggregation over the live `domain` table.** Country/ASN/classification
  rollups are read from the precomputed `stats_*` daily tables, never `GROUP BY domain`
  live.

*Note on "recently changed."* The draft offered a `-last_change` sort; it is **dropped** — no
`last_change` column or index exists (the `domain` table has `updated_at`, `last_checked_at`,
and six per-dimension `*_since` columns, but no single last-change timestamp), and the keyset
design (§4.2) requires every sort to bind an indexable strict total order. "What changed
recently" is served natively by the changelog feed (§5.8, indexed on `ts`). If a sorted
"recently changed domains" leaderboard is later wanted, it needs a materialized, indexed
`last_change = GREATEST(base_since, …, resources_since)` column — flagged **OPEN-14**.

### 4.4 Count strategy

**Decision.** **No exact `COUNT(*)` on the hot path.** Exact counts over a million MVCC
rows scan every visible row and are "seldom useful on the pagination path." Counts always
live in `meta` (§3.4), never as an `items`-sibling.

- The **global list** `meta.count_estimate` is served from **`max(rank)` of the current
  generation** — an O(1) lookup, an exact-ish "how many ranked domains" and the "your rank /
  ~N" denominator, but labelled an **estimate** because disabled ranked rows create small
  gaps (§4.1).
- **Filtered global views and the country/asn-scoped lists** get an **estimated**
  `count_estimate` (`reltuples` for the unfiltered table; the EXPLAIN plan row estimate for a
  filtered query). These scopes can be very large (§4.1), so an exact count is never taken.
- **Bounded curated sets** (campaign members, `/shame`, forward-resources) get an **exact**
  `meta.count` — the result set is a few tens of rows and exact is trivially cheap there.

`has_more` on every page is computed with the **N+1 fetch** (select `limit+1`, return
`limit`), avoiding a second query.

*Rejected — offset with a total on any large list.* Both halves are the expensive pattern
the research warns against: deep offset scans and per-request `COUNT(*)`.
*Rejected — a cached materialized exact count.* Unnecessary; `max(rank)` already gives the
ranked total for free, and estimates suffice for filtered/scoped views.

## 5. The resource model

Every representation serves the **real** status/classification/gold/flags model. The
canonical building block is the domain row; everything else composes from it.

### 5.1 Domain — the status object convention

Each of the six dimensions is a **status object**, not a flat string, so per-dimension
provenance rides along:

```json
"status": {
  "base":      { "value": "supported",    "since": "2024-11-03T00:00:00Z" },
  "www":       { "value": "supported",    "since": "2025-01-19T00:00:00Z" },
  "ns":        { "value": "supported",    "since": "2023-08-01T00:00:00Z" },
  "mx":        { "value": "unsupported",  "since": "2025-06-02T00:00:00Z" },
  "conn":      { "value": "supported",    "since": "2025-01-19T00:00:00Z" },
  "resources": { "value": null,           "since": null }
}
```

`value` is the 4-value enum (`supported`/`unsupported`/`no_record`/`not_applicable`) **or
JSON `null`** when the dimension has never been confirmed (`resources` is `null` everywhere
until `crawler.resources.enabled` flips). `since` is the `*_since` column (when the
confirmed value last changed), `null` when never confirmed. **This is the whole point of
the redesign:** no `legacyStatus` collapse of `not_applicable`/never-confirmed into
`no_record`, no `ts_aaaa`/`ts_www` key renaming, no `"0001-01-01T00:00:00Z"` zero-time
encoding — real enum, real names, `null` for absent.

### 5.2 Domain summary (list row)

The row returned in every `/domains*` collection:

```json
{
  "host": "example.com",
  "rank": 10023,
  "kind": "apex",
  "parent": null,
  "classification": "partial",
  "class_flags": ["www_missing", "mail_missing"],
  "gold": false,
  "status": {
    "base":      { "value": "supported",   "since": "2024-11-03T00:00:00Z" },
    "www":       { "value": "unsupported", "since": "2025-05-10T00:00:00Z" },
    "ns":        { "value": "supported",   "since": "2023-08-01T00:00:00Z" },
    "mx":        { "value": "unsupported", "since": "2025-06-02T00:00:00Z" },
    "conn":      { "value": "supported",   "since": "2025-01-19T00:00:00Z" },
    "resources": { "value": null,          "since": null }
  },
  "country": { "code": "NO", "name": "Norway" },
  "asn":     { "number": 2119, "name": "Telenor Norge AS" },
  "last_checked_at": "2026-07-07T02:14:55Z"
}
```

`rank` is `int` or **JSON `null`** (campaign-only, subdomains, live-check hosts) — never
the legacy `0`. `class_flags` is served as the ordered array
(`broken_v6`/`www_missing`/`ns_missing`/`mail_missing`/`resources_v4only`); a `partial`
domain may legitimately carry `[]`. `country`/`asn` are **embedded objects** (code+name,
number+name), not the legacy display-name strings under misnamed keys. `?fields=` can trim
this to e.g. `host,rank,classification,gold` for a dense leaderboard table.

### 5.3 Domain detail

`GET /domains/{host}` — the summary plus informational dimensions, children, and a
freshness/meta block. The heavy per-check evidence (record sets, TLS cert, per-resolver
consensus tuples, resource lists) is served from the latest `scan_detail` under a nested
`evidence` object (same shape as the live-check result, §6.1 — the shared `MapLiveResult`
mapper), so the detail page and the live check render identically.

```json
{
  "host": "example.com",
  "rank": 10023,
  "kind": "apex",
  "parent": null,
  "classification": "partial",
  "class_flags": ["www_missing", "mail_missing"],
  "gold": false,
  "status": { "...": "six status objects as in §5.1" },
  "informational": {
    "dnssec": "supported",
    "ptr":    "partial",
    "smtp":   "unsupported",
    "parity": "supported",
    "latency_v4_ms": 41,
    "latency_v6_ms": 38
  },
  "country": { "code": "NO", "name": "Norway", "tld": ".NO" },
  "asn":     { "number": 2119, "name": "Telenor Norge AS" },
  "subdomain_count": 3,
  "disabled": false,
  "last_checked_at": "2026-07-07T02:14:55Z",
  "created_at": "2022-05-01T00:00:00Z",
  "evidence": { "...": "latest scan_detail JSONB, per §6.1 shape (optional, ?include=evidence)" },
  "meta": { "as_of": "2026-07-07T03:41:12Z", "generation": 20260707 }
}
```

`informational` dimensions are **advisory** — they never gate classification. They are
served as latest-observation values, but with the **same public-masking rule the trust
model requires everywhere on the wire** (03 §1 / the 05 enum registry: `error` and
`inconsistent` never reach public output; `partial` is public only for `ptr`/`parity`).
Concretely, per field:

| Field | Allowed wire values |
|---|---|
| `dnssec` | `supported` \| `unsupported` \| `no_record` \| `not_applicable` \| `null` |
| `smtp` | `supported` \| `unsupported` \| `no_record` \| `not_applicable` \| `null` |
| `ptr` | above **plus** `partial` |
| `parity` | above **plus** `partial` |

A latest observation of `error` or `inconsistent` maps to **`null`** (never leaks). A raw
`partial` on `dnssec`/`smtp` (not one of the two fields where `partial` is public) also maps
to `null`. `subdomains[]` are a native sub-collection (`/domains/{host}/subdomains`), not the
legacy "additive keys the frozen frontend ignores" bolt-on. Observation-level richness
(`error`/`inconsistent`) is exposed **only** inside `evidence` (OPEN-3), honoring the trust
model's "observations are telemetry, only confirmed status is public."

#### Additional per-domain attributes to store (2026-07-09)

The design already stores `asn_id` and `country_id` per domain. These additional league-table
pivots are decided; they are schema additions to fold into 05-schema.md when this report is
folded into the spec (see §10.3):

- **`tld`** — the domain's TLD / eTLD suffix (e.g. `com`, `no`, `gov`), derived for free from
  the host at ingest (publicsuffix). Enables TLD / ccTLD registry league tables (which
  registries / countries lead on IPv6). Low cost, high leverage. **Add now.**
- **DNS-provider** — the `ns_host → provider` mapping (already committed via OPEN-4). The
  **highest-leverage pivot** — one provider's default flips thousands of domains. **Add now.**
- **Hosting/CDN provider** — a normalized `hosting`/`cdn` provider tag, mostly derivable from
  data already collected (the checker's CNAME-chain CDN detection + the resolved IP's ASN).
  Enables "which CDN hosts the most sinners." **Add** as the companion to the DNS-provider
  axis.
- **Registrar** — **defer.** Enables registrar league tables but requires RDAP lookups at 1M
  scale (rate-limited, often redacted, real ingestion cost). Want-it-later, not round-1.

The API resource model should expose **`tld`** and the provider fields on the domain resource
(§5.2/§5.3) and as filter/pivot axes (`?tld=`, `?provider=`), under the same indexed-scope
guardrail as the per-dimension/flag filters (OPEN-2, §4.3).

### 5.4 The ranked tier lists

Heroes / sinners / gold / almost / mail are **first-class short collection resources** — each
a preset filtered view over the `/domains` leaderboard, returning the §5.2 summary row in the
§3.4 collection envelope, sharing the exact same keyset/cursor pagination and `?country=`/
`?asn=` filter composition. These are the canonical, shareable browse URLs the frontend links
to:

```
GET /heroes             # preset: class=hero
GET /sinners            # preset: class=sinner
GET /gold               # preset: gold=true
GET /almost             # the "almost there" list — partial domains one step from hero
GET /mail               # the mail/MX heroes track
```

`GET /domains` stays the **general filterable collection**; the same views are reachable
through it via the `?class=` param (`GET /domains?class=hero&sort=rank`,
`GET /domains?class=sinner`, `GET /domains?class=partial`, `GET /domains?class=hero&gold=true`).
Tier paths accept the same additional filters, so "sinners in Norway" is
`GET /sinners?country=no` (equivalently `GET /domains?class=sinner&country=no`), and the
scoped `GET /countries/{code}/domains?class=sinner` also works.

**The mail track** (feature-research #10) obeys the §4.3 scope-or-stats guardrail:

- **Mail-heroes** — `GET /mail` is the canonical path (preset `class=hero&mx=supported`,
  scoped so `mx=` is indexed via the `class` prefilter).
- **Mail-sinners** `GET /domains?class=sinner&mx=unsupported` (likewise scoped). A truly
  *global* mail-sinners count (every domain with `mx=unsupported`, regardless of
  classification) is **not** a live `/domains` scan — that headline number is read from the
  `mx_supported` daily stats counter (`domains − mx_supported`). The list form is always
  class/country/asn-scoped.

**The top-shame editorial pick** (hand-curated `top_shame`, distinct from algorithmic
`sinner`) is its own resource, and — like every collection — returns the envelope, not a bare
array:

```
GET /shame
```
```json
{
  "items": [ { "host": "...", "reason": "...", "added_at": "..." } ],
  "page": { "next_cursor": null, "prev_cursor": null, "has_more": false },
  "meta": { "as_of": "...", "generation": 20260707, "count": 12 }
}
```

It is a small bounded editorial list (the ~12 curated picks, §9/§10.4), so no cursor is
needed — `page` is trivial and `meta.count` is exact.

### 5.5 Country

```json
{
  "code": "NO",
  "name": "Norway",
  "tld": ".NO",
  "sites": 8421,
  "v6_sites": 2103,
  "percent": 24.97,
  "meta": { "as_of": "...", "generation": 20260707 }
}
```

`v6_sites` is the snake_case-normalized wire name for the schema column `country.v6sites`
(§3.3, mechanical case-normalization). `percent` is served **directly** from the
`NUMERIC(5,2)` column (the legacy `÷10` pgtype hack is gone). `GET /countries` is the
leaderboard, sortable by `percent`/`v6_sites` (precomputed counters → cheap, no live
aggregation). `GET /countries/{code}/domains` is the per-country list
(`?class=` filter over `idx_domain_country`) — **keyset-paginated with a
`count_estimate`**, because a large country can hold hundreds of thousands of domains (§4.1),
not a bounded sub-list. Time series: `GET /countries/{code}/stats` (§5.10). The `UN`
sentinel appears as a normal row.

### 5.6 ASN / provider

```json
{
  "number": 2119,
  "name": "Telenor Norge AS",
  "count_total": 4210,
  "count_v6": 1876,
  "count_v4": 2334,
  "meta": { "as_of": "...", "generation": 20260707 }
}
```

`count_v4` is **synthesized server-side** (`count_total − count_v6`) — not stored.
`count_v6`/`count_total` are the **canonical wire names for the "v6-capable / total domains
in this network" concept, used in both this detail representation and the ASN time-series
(§5.10)** — the time-series' underlying `stats_asn_daily.v6_domains` column is mapped onto the
same `count_v6` wire name so the concept has one spelling across the two representations
(§3.3). `GET /asns` is the network leaderboard (`?sort=count_v6|count_total`; real columns,
no `order=ipv4|ipv6` alias, no AS-prefix search bug — `?q=` does normal substring match).
`GET /asns/{number}/domains` lists the network's domains — **keyset-paginated with a
`count_estimate`**, because a hyperscaler ASN can host tens to hundreds of thousands of
eTLD+1s (§4.1), not a bounded sub-list. The sentinel `0` = Unknown appears as a normal group.
This is also the **hosting-ASN league table** (feature-research #2). The **DNS-provider
league table** (OPEN-4, resolved YES 2026-07-09) is **committed**: a new `ns_host → provider`
mapping table derived from collected NS data (§10.3) backs `/providers` +
`/providers/{id}/domains`, exposing binary inclusion + counts only (no scores). It is the
highest-leverage pivot — one provider's default flips thousands of domains. A companion
**hosting/CDN provider** axis (derived from CNAME-chain CDN detection + resolved-IP ASN) is
likewise added (§5.3 additional attributes).

### 5.7 Campaign (composite detail)

`GET /campaigns` lists campaigns; the detail is a **composite** (metadata + paged members
+ adoption), the genuine frontend need:

```json
{
  "uuid": "3f2b...",
  "name": "Norwegian Banks",
  "description": "Retail banks operating in Norway",
  "source_file": "campaigns/no-banks.yaml",
  "disabled": false,
  "adoption": { "v6_ready_percent": 41.7, "day": "2026-07-07" },
  "domains": {
    "items": [ /* §5.2 domain summary rows, typically rank:null */ ],
    "page": { "next_cursor": null, "prev_cursor": null, "has_more": false }
  },
  "meta": { "as_of": "2026-07-07T03:41:12Z", "generation": 20260707, "count": 17 }
}
```

Members are ordinary domain rows joined via `campaign_domain`, **ordered by `host` and paged
with the same keyset cursor as every other collection** (§4.2 — `host` is a unique key, so
the seek is total even though members' `rank` is usually NULL). Campaign members are the one
genuinely-bounded members set, so `meta.count` is **exact**. The composite `page` object has
the uniform three-field shape (`next_cursor`/`prev_cursor`/`has_more`) — no offset, no
`next_cursor`-only object. `adoption.v6_ready_percent` comes from `stats_campaign_daily`
(`v6_ready` = base supported ∧ ns supported ∧ www ∈ {supported, not_applicable}), never
per-entity scoring; `adoption.day` is the stats date (date granularity, §3.4). Keyed by
**raw UUID**, not shortuuid. Time series: `GET /campaigns/{uuid}/stats`.

### 5.8 Changelog event (the trust surface)

Served **structured**, one row per confirmed dimension transition — no message rendering,
no synthetic epoch id, no `domain_url` string:

```json
{
  "ts": "2026-07-06T03:32:10Z",
  "host": "example.com",
  "field": "www",
  "old_value": "unsupported",
  "new_value": "supported"
}
```

`ts` is a full RFC 3339 **timestamp** (event time). `old_value`/`new_value` are the raw
4-value enum, always non-null, always distinct. **All native fields are served**, including
`conn` and `resources` transitions and `not_applicable` transitions — the legacy R5 coverage
filter (which admitted only `base/www/ns/mx` with 3 legacy strings) is deleted. Feeds:

- `GET /changelog` — global recent-transitions feed, cursor on `ts DESC`
  (`idx_changelog_ts`), `?field=` and `?from=/&to=` windows.
- `GET /domains/{host}/changelog` — per-domain (native PK read).
- `GET /campaigns/{uuid}/changelog` — campaign-wide (members' transitions).
- `GET /campaigns/{uuid}/domains/{host}/changelog` — one member.
- `GET /countries/{code}/changelog` — **new** per-country feed (no legacy equivalent).

**Scoped-feed cost (from the review — the §4.3 discipline applies here too).** The
`changelog` hypertable is keyed `(domain_id, ts, field)` with a global `idx_changelog_ts` and
the per-domain PK — but **no `(scope_id, ts)` index**. A naive per-country / per-campaign feed
(`changelog JOIN domain WHERE country_id=X ORDER BY ts DESC`, or a join through
`campaign_domain`) can scan far back through the global `ts` index probing membership for a
sparse scope. To keep these feeds bounded and cheap, the scoped changelog feeds (per-country,
per-campaign) are **capped to a fixed recent window** — the latest 50 transitions (matching
the feed policy in §6.4), never deep-paginated; bulk consumers are steered to the datasets
(§6.3). A denormalized `(country_id/campaign, ts)` path — either stamping `country_id` onto
`changelog` or a scoped-feed continuous aggregate — is flagged **OPEN-15**; until it exists,
the recent-window cap is the guardrail (the same rationale used for the `flag=` filter). The
global and per-domain feeds are already index-backed and paginate normally.

The item id for feed serializations (§6.4) is the composite `(host, ts, field)` (stable,
immutable), not the legacy epoch-millis synthetic id.

### 5.9 Per-domain timeline / history

`GET /domains/{host}/history?from=&to=&interval=daily|weekly` — the trajectory graph.

**Trust-consistent sourcing (important).** The per-dimension trajectory is **reconstructed
from the `changelog`** (the authoritative confirmed transitions, the same source as §5.8),
**not** read from the raw `scan` hypertable. This is deliberate: `scan` columns are the raw
`observation` enum (`supported|unsupported|no_record|not_applicable|error|inconsistent`),
which would (a) leak `error`/`inconsistent` into public output — locked as "never reach public
output" (03 §1) — and (b) mix a noisy per-scan observation trajectory with the smooth
confirmed one (a user would see `mx` flip supported/unsupported day-to-day while
`classification` stayed `partial`). Instead the API **replays the changelog** to reconstruct
the confirmed per-dimension state as of each day in the window, and applies the deterministic
classification ladder to those confirmed values to stamp `classification` per point — a pure
function of confirmed state, fully trust-consistent. The only value taken from `scan` is the
**latency overlay** (`latency_v4_ms`/`latency_v6_ms`), a genuinely per-scan measurement that
carries no confirmed-status semantics.

```json
{
  "host": "example.com",
  "points": [
    {
      "day": "2026-07-01",
      "base": "supported", "www": "supported", "ns": "supported",
      "mx": "unsupported", "conn": "supported", "resources": null,
      "classification": "partial",
      "latency_v4_ms": 41, "latency_v6_ms": 38
    }
  ],
  "meta": { "retention_days": 730, "as_of": "..." }
}
```

`day` is date granularity (§3.4). `resources` is `null` (never confirmed, per §5.1 — until
`crawler.resources.enabled` flips) — this is the confirmed-never `null`, correct here because
the source is the confirmed reconstruction, not a `scan` observation. No pagination (bounded
by the date window, `points` collection, §3.4); `interval=weekly` samples the reconstructed
state at each week boundary, not averaging. **Day-1 note:** because the trajectory is
changelog-sourced, the optional history import (§9) populates it directly; the fresh-scan
**latency overlay** is the only part that starts empty and fills as scans accumulate.

### 5.10 Stats / overview (adoption over time)

Five routes, one query contract (`?from=&to=&interval=daily|weekly`, default `to=today`,
`from=to−90d`, ascending, no pagination, `≤366 rows/yr`, zero rows → `200 {"points":[]}`),
sourced from the confirmed-state `stats_*_daily` tables so graphs match public lists
exactly. All use the `{points, meta}` time-series envelope (§3.4):

- `GET /stats/overview` — `stats_global_daily` (the headline dashboard).
- `GET /countries/{code}/stats` — `stats_country_daily`.
- `GET /campaigns/{uuid}/stats` — `stats_campaign_daily` (incl. `v6_ready%`).
- `GET /asns/{number}/stats` — `stats_asn_daily` (exposes the `count_v6`/`count_total`
  wire names, §5.6).
- `GET /domains/{host}/history` — per-domain, changelog-reconstructed (§5.9).

The overview point carries the full `stats_global_daily` payload:

```json
{
  "points": [
    {
      "day": "2026-07-06",
      "domains": 1003418, "heroes": 41022, "partial": 88310, "sinners": 210144,
      "inactive": 512900, "unknown": 151042, "gold": 3110, "disabled": 8933,
      "base_supported": 260113, "www_supported": 241889, "ns_supported": 402231,
      "mx_supported": 180334, "conn_supported": 251004, "resources_supported": 0,
      "top_heroes": 512, "top_nameserver": 690
    }
  ],
  "meta": { "as_of": "...", "source": "confirmed_state" }
}
```

`meta.source: "confirmed_state"` is deliberate: if the measurement-flavored
`scan_daily_adoption` cagg is ever exposed (OPEN-5), it must be labelled
`source: "measurement"` and never reconciled with these numbers — it wobbles with scan
timing and includes unconfirmed values.

### 5.11 Resource dependencies

- `GET /domains/{host}/resources` — forward: what this domain depends on. Bounded small
  (a handful of resource hosts per domain), so no cursor is needed — but it still returns the
  uniform collection envelope (`items`, not a bare `resources` key), `ORDER BY host`, with an
  exact `meta.count`:

```json
{
  "items": [
    { "host": "fonts.googleapis.com", "aaaa_status": "unsupported",
      "source": "discovered", "required": true,
      "first_seen": "2025-02-01", "last_seen": "2026-07-06",
      "last_checked_at": "2026-07-07T01:00:00Z" }
  ],
  "page": { "next_cursor": null, "prev_cursor": null, "has_more": false },
  "meta": { "as_of": "...", "generation": 20260707, "count": 4 }
}
```

- `GET /resources/{host}/dependents` — reverse: **the advocacy surface**
  ("this v4-only host breaks N sites"), keyset-paginated over the **null-flag-first**
  ordering (`ORDER BY (rank IS NULL), rank, id`, §4.2 — the set mixes ranked and rank-NULL
  dependents, so the plain `(rank, id)` seek would drop the null-rank tail):

```json
{
  "resource": { "host": "fonts.googleapis.com", "aaaa_status": "unsupported",
                "dependent_count": 41022, "last_checked_at": "..." },
  "items": [ /* §5.2 domain summary rows depending on it */ ],
  "page": { "next_cursor": "...", "prev_cursor": null, "has_more": true },
  "meta": { "as_of": "...", "generation": 20260707, "count_estimate": 41022 }
}
```

`resource.dependent_count` is the headline counter; the paged `items` carry a
`meta.count_estimate` because the dependent set can be very large. This powers the
`resources_v4only` flag narrative and the highest-leverage "one provider fix unlocks
thousands" pressure. Empty/dormant until `crawler.resources.enabled` flips.

not a wire quirk. Echoes the caller's real IP (bracketless), redesigned to an object:

## 6. Special endpoints

### 6.1 Live check — async job lifecycle

Anonymous, no auth; the only write path. **Async enqueue + poll**, never synchronous (a
full engine run is 60–90 s; holding an anonymous request open invites resource exhaustion).

```http
POST /check
Content-Type: application/json

{ "host": "example.com" }
```

```http
HTTP/1.1 202 Accepted
Location: /check/481529
Cache-Control: no-store

{ "id": 481529, "host": "example.com", "status": "pending", "created_at": "..." }
```

```http
GET /check/481529     → 200 { "id": 481529, "host": "...", "status": "done", "cached": false, "result": { ... } }
```

**Job id type.** The job `id` is the schema's **`BIGINT GENERATED ALWAYS AS IDENTITY`**
(`check_job.id`), served as an integer on the wire — consistent with 05-schema.md and with
07-api.md's existing acceptance that sequential ids are fine for anonymous public data
(nothing sensitive; the results are about public domains and are purged after 30 d). This is
**not** the draft's ULID token, which would have been an unflagged schema change. *If*
unguessable poll tokens are later judged worthwhile, changing `check_job.id` to UUIDv7/ULID is
a deliberate schema change to be listed in §10.3 with that rationale — flagged, not assumed.

`status ∈ pending|processing|done|failed`; the client polls until terminal. `result` is the
shared-mapper (`MapLiveResult`) output — **raw observations**
(`supported|unsupported|no_record|not_applicable|error`, plus `inconsistent` on a quorum
split) **plus a read-time `confirmed` object** — explicitly *not* confirmed state. Dedicated
worker pool claims jobs with `FOR UPDATE SKIP LOCKED`; 60 s per-job budget; a reaper flips
stale jobs to `failed`; rows purged after 30 d.

**Poll caching (from the review).** The poll endpoint is otherwise the one anonymous read
path the CDN cannot absorb (`no-store`, excluded from the rate limiter). To close that gap
cheaply, **terminal responses are cacheable**: a `done`/`failed` job is immutable, so it is
served `Cache-Control: public, max-age=60` (a job id is minted per request, so this is safe);
`pending`/`processing` stay `no-store`. Recommended client poll interval is **2 s** (the
worker pool already polls at 2 s); the OpenAPI documents it. This bounds poll pressure without
adding a limiter to a read path.

**Rule 0 (locked):** the live check writes only `check_job.result` and **never advances
confirmed state** — no `scan` rows, no `*_pending`/`*_observed`, no `last_checked_at`, no
`classification`, no `changelog`. Anonymous POSTs must not accelerate the N-consecutive-scan
confirmation. Lifecycle re-entry may set `last_requested_at`/`next_check_at` and re-enable
dead/delisted rows (schedules frontier work, never advances state).

**Anti-abuse.** Two dedupe layers within a 1 h window (domain-side from latest
`scan_detail`; job-side from a recent `done` job) return `200` with `"cached": true` and no
new job row. Rate limits (§7.3) are per-IP and global, `429 rate-limited` + `Retry-After`.
The **retest-now button** (feature-research #3) on every red page reuses this queue as a
priority re-scan; no new endpoint.

Errors are RFC 9457: invalid host → `400 invalid-parameter`; non-JSON body →
`415 unsupported-media-type`; over quota → `429 rate-limited`.

### 6.2 Embeddable SVG badge

`GET /badge/{host}.svg` — a shields.io-flat SVG rendered from confirmed status.

- `Content-Type: image/svg+xml; charset=utf-8` (overrides the JSON default);
  `Cache-Control: public, max-age=86400` (daily crawl cadence); `X-Content-Type-Options:
  nosniff`; an `ETag` from the crawl generation; **no rate-limit** (CDN-cacheable).
- Six precompiled byte-deterministic variants, one per `classification`(+`gold`) input.
  Copy is **public status vocabulary**, never ladder branding — a README badge never says
  "sinner"/"hero". The mapping is normative:

| `classification` (+ `gold`) | SVG message label | shields color | `isError` (JSON variant) |
|---|---|---|---|
| `hero` | `IPv6: supported` | `brightgreen` | `false` |
| `hero` + `gold: true` | `IPv6: gold` | `brightgreen` (gold accent) | `false` |
| `partial` | `IPv6: partial` | `yellow` | `false` |
| `sinner` | `IPv6: no IPv6` | `red` | `false` |
| `inactive` | `IPv6: inactive` | `lightgrey` | `false` |
| `unknown` | `IPv6: unknown` | `lightgrey` | `true` |

  These six inputs (the five `classification` enum values plus the `gold` overlay on `hero`)
  are the complete, unambiguous badge vocabulary — the draft's earlier
  `supported/partial/no record/gold`-only copy list was incomplete. `sinner`'s label is
  `no IPv6` (not "unsupported" or "no record"). `unknown` sets `isError:true` (§below) so
  shields renders it as a genuine error and won't let a user recolor it.
- **Read-only, zero side effects:** never inserts a domain row, never enqueues a check_job,
  never touches `last_requested_at`. Not rank-scoped (any kind/origin resolves).
- The `.svg` suffix is part of the route pattern, not the `{host}` param; a suffix-less
  path is a route-miss `404`.
- **Declared exception to the 404-on-canonicalize-failure rule:** an invalid host →
  `400 invalid-parameter` JSON (a malformed host is not a legitimate embed). A *valid* host
  is **always `200`** (a `404` renders as a broken image); disabled/unknown → the gray
  `IPv6: unknown` badge. XML-escape the host label into the SVG to prevent markup injection.

**Also offer the shields.io endpoint-JSON variant** for users who want shields styling:
`GET /badge/{host}.json` → `{"schemaVersion":1,"label":"IPv6","message":"supported",
"color":"brightgreen","cacheSeconds":86400,"isError":false}`. Its `message`/`color`/`isError`
come from the table above. This JSON deliberately uses shields.io's **camelCase** field names
(`schemaVersion`/`cacheSeconds`/`isError`) — the one sanctioned camelCase exception (§3.3),
dictated by shields.io's external schema. Users embed
`https://img.shields.io/endpoint?url=https://api.whynoipv6.com/badge/example.com.json`.
Feature-research ranks the badge **#1** (viral distribution; every badge is a backlink) —
promote it from "optional" to committed.

### 6.3 Datasets — static bulk + manifest + citation

Bulk data is a **separate static channel**, not the paginated API (keeps scrapers off the
pagination path; avoids CrUX's BigQuery-only mistake that spawns unofficial mirrors).

- **Served statically by nginx** under `/datasets/` (not the API). API-generated on-demand
  exports and S3 were both rejected — a directory + nginx is the solution. Nightly
  `v6ctl export` produces, atomically (tmp-dir `rename(2)`), 3 size tiers (`top100k`,
  `top1m`, `full`) × formats **CSV.gz + Parquet** (+ optionally JSONL for the append-only
  changelog history). Columns: `host, rank, kind, parent, classification, class_flags,
  gold, {6 confirmed statuses}, {6 since-timestamps}, country, asn, last_checked`.
  `top100k`/`top1m` use the publicly-ranked predicate; `full` = all non-disabled scannable
  entities. Dailies retained 90 d, first-of-month forever.
- **Self-describing + verifiable:** each snapshot ships a Frictionless **`datapackage.json`**
  — a `resources[]` array with per-file `path`, `bytes`, `hash: "sha256:<digest>"` (always
  the `sha256:` prefix; a bare hash means MD5 to the spec), and a Table Schema of column
  names/types — plus a `SHA256SUMS` file and a `DICTIONARY.md`.
- **The top-level `manifest.json` (the one file the API serves, §below) is a distinct index
  over snapshots, not an alias of a per-snapshot `datapackage.json`.** Its schema is pinned:

```json
{
  "schema_version": 1,
  "generated_at": "2026-07-07T04:10:00Z",
  "generation": 20260707,
  "license": "CC-BY-NC-4.0",
  "attribution": "Data: whynoipv6.com (CC-BY-NC-4.0). Ranks: Tranco list <id>.",
  "latest": {
    "date": "2026-07-07",
    "path": "datasets/2026-07-07/",
    "datapackage_url": "/datasets/2026-07-07/datapackage.json"
  },
  "snapshots": [
    {
      "date": "2026-07-07",
      "path": "datasets/2026-07-07/",
      "tiers": ["top100k", "top1m", "full"],
      "formats": ["csv.gz", "parquet"],
      "datapackage_url": "/datasets/2026-07-07/datapackage.json",
      "sha256sums_url": "/datasets/2026-07-07/SHA256SUMS"
    }
  ]
}
```

  `schema_version` (int) versions this index shape and the exported column set, and bumps
  whenever either changes. Each `snapshots[]` entry points at that snapshot's
  `datapackage.json` (which in turn lists the actual files, hashes, and Table Schema). This
  `manifest.json` schema is added to the OpenAPI `components` so the drift gate (§8) contract-
  tests it like any other response.
- **Citable:** the **dated (immutable) path** is the citation anchor; a stable
  `/datasets/latest/whynoipv6-top1m.csv.gz` alias is the convenience URL for scripts. An
  optional **Zenodo Concept DOI** (all versions) + per-snapshot **Version DOI** (monthly/
  quarterly cadence to avoid DOI sprawl) is a later additive step gated on demand (OPEN-6);
  it is a manual/API step outside the daily crawler.
- **License in-band:** **CC-BY-NC-4.0** (fits the non-commercial constraint) stated in the
  manifest, the OpenAPI `info` block, and the `DICTIONARY.md`, with a required attribution
  string. **Tranco rank redistribution (constraint-adjacent, OPEN-13).** CC-BY-NC-4.0 covers
  *our* derived measurements; it does **not** by itself grant the right to redistribute
  Tranco's ranking, which the datasets re-publish as a `rank` column across all three tiers.
  Before shipping `rank` in bulk, verify Tranco's redistribution/citation terms and state
  them in-band (cite the specific Tranco list ID/permalink used in `DICTIONARY.md` +
  `datapackage.json` + the manifest `attribution` string, honor its attribution requirement);
  **if Tranco restricts bulk rank redistribution, omit `rank` from the public bulk export (or
  gate it)** while keeping the per-entity `rank` on the live API. Flagged as OPEN-13 alongside
  OPEN-6; it could otherwise block the headline dataset/citation deliverable.

**The only dataset piece the API serves:** `GET /datasets` re-reads
`$DATASETS_DIR/manifest.json` from disk every request and returns it verbatim (the schema
above) as `application/json`, `Cache-Control: public, max-age=300`. Missing/unparseable →
`503 manifest-unavailable` (the only 503). nginx location split: exact `=/datasets` → API;
dated dirs → immutable 1 yr cache; `latest/` + `DICTIONARY.md` → 1 h cache.

### 6.4 Change feeds — Atom + JSON Feed per scope

The changelog is the only account-free **push** channel and near-zero cost (it's just the
structured changelog rendered as a feed). Feed representations are exposed as **distinct
suffix URLs** (keeps CDN cache keys clean; embeddable in READMEs/feed readers with no header
control), per scope:

| Scope | Atom | JSON Feed 1.1 |
|---|---|---|
| Global | `/changelog.atom` | `/changelog.feed.json` |
| Per-domain | `/domains/{host}/changelog.atom` | `.feed.json` |
| Per-campaign | `/campaigns/{uuid}/changelog.atom` | `.feed.json` |
| Per-country | `/countries/{code}/changelog.atom` | `.feed.json` |

The extension-less path stays the paginated JSON-API list (§5.8).

**Feed-level contract (concrete, so the four-scope × two-format matrix is mechanically
generable).** Every feed is a **fixed recent window of the latest 50 transitions, no
pagination** (bulk consumers are steered to the datasets, §6.3; this also honors the scoped-
feed cost cap in §5.8). Required top-level members, with their sources:

- **Atom (RFC 4287, `application/atom+xml`):** feed `<id>` = the scope's canonical API URL
  (e.g. `https://api.whynoipv6.com/countries/NO/changelog`); `<updated>` = `max(ts)` in
  the window; `<title>` = the scope name ("WhyNoIPv6 — Norway", "WhyNoIPv6 — example.com",
  global "WhyNoIPv6 — recent changes"); `<link rel="self">` = the `.atom` URL,
  `<link rel="alternate">` = the extension-less JSON list URL.
- **JSON Feed 1.1 (`application/feed+json`):** `version`
  (`https://jsonfeed.org/version/1.1`), `title` (scope name), `home_page_url` (the
  extension-less list URL), `feed_url` (the `.feed.json` URL), and `items`.

Per item: `id`/`guid` = the composite `(host, ts, field)`; `date_published` = `ts` (RFC
3339); the human `title`/`content_text` is derived **server-side at render time** from
`(field, old_value, new_value)` — e.g. "example.com now supports IPv6 on www" — *freshly*,
not from the deleted frozen 16-row message table. Per-scope feeds mean subscribers aren't
forced to the firehose.

### 6.5 CSV export via content negotiation

Feature-research #7 (internet.nl ships exactly this; near-free amplification). **`?format=csv`**
on the list endpoints (`/domains*`, `/countries`, `/asns`, `/changelog`, search results) —
the Radar precedent, and a query param keeps the CDN cache key clean and the shareable URL
stable. `Content-Type: text/csv; charset=utf-8`, `Content-Disposition: attachment`. A
defined column set per list (the summary-row columns for `/domains`). The stable, cursor- or
`after_rank`-anchored URL means a shared link reproduces the same view. Larger "give me
everything" pulls are steered to the static datasets (§6.3), not deep CSV pagination.

*Rejected — `Accept: text/csv` negotiation for CSV.* The suffix/`?format` approach yields
clean per-representation cache keys and human-shareable URLs; `Accept`-based negotiation on
the same URL needs `Vary: Accept` and is invisible in a shared link. `Accept` is reserved
for the JSON core (default `application/json`; `406 not-acceptable` when unsatisfiable).

## 7. Caching, content negotiation, rate limiting, compression

Daily-batch, fully-public data behind a CDN is the ideal caching case; caching + a CDN is
the single biggest performance lever for an anonymous read-heavy site facing viral traffic.

### 7.1 Caching by endpoint class

| Class | `Cache-Control` | Validators |
|---|---|---|
| List / leaderboard / stats (`/domains*`, `/countries*`, `/asns*`, `/stats/*`, `/changelog`) | `public, max-age=300, s-maxage=<until-next-crawl>, stale-while-revalidate=600, stale-if-error=86400` | `ETag` from crawl `generation` (+ query fingerprint); `Last-Modified` from crawl ts; honor `If-None-Match` → `304` |
| Domain / country / asn / campaign detail | as above; ETag tied to that entity's last confirmed transition | `304` on `If-None-Match` |
| Badge SVG/JSON (`/badge/*`) | `public, max-age=86400` | `ETag` from generation |
| Datasets manifest (`/datasets`) | `public, max-age=300` | — |
| Static datasets (nginx) | dated dirs `immutable, max-age=31536000`; `latest/` `max-age=3600` | nginx auto ETag |
| Live check poll (`GET /check/{id}`) — **terminal** (`done`/`failed`) | `public, max-age=60` (immutable job) | — |
| Live check (`POST /check`, `GET /check/{id}` while `pending`/`processing`), `/ip` | `no-store` | — |
| Health (`/livez`,`/readyz`) | `no-store` | — |

Use `public` (never `private`) — there is no per-user data, and `public` is what unlocks CDN
edge caching. **ETags must be deterministic across backend instances** for the same content —
derive from the crawl `generation` (`= YYYYMMDD` of `max(stats_global_daily.day)`, §3.4) +
query fingerprint (for lists) or the entity's last confirmed-transition ts (for detail), never
from a per-process hash. Prefer explicit generation-keyed cache keys over guessing TTLs, since
content changes exactly once per crawl.

### 7.2 Content negotiation

`Accept`-header negotiation for the JSON core (default `application/json`; `406` when
unsatisfiable, as a Problem Detail). Genuinely-different representations are **distinct
URLs**, not `Accept` variants: badge `.svg`/`.json`, feeds `.atom`/`.feed.json`, CSV
`?format=csv`. Set `Vary: Accept` on any Accept-negotiated endpoint and `Vary:
Accept-Encoding` everywhere compression applies, so shared caches never serve the wrong
representation.

### 7.3 Rate limiting

**Only `POST /check` is rate-limited** — cacheable GETs (including the now-cacheable terminal
poll responses, §6.1) are absorbed by the CDN and need no limiter (RIPEstat/ip-api model:
per-IP quota, no keys). Keyed on the **CDN-forwarded real client IP** (not the proxy IP):
per-IP `live_check.rate_ip_per_hour` (default 10) and global
`live_check.rate_global_per_hour` (default 500), counted over `check_job` rows in a 1 h
window. On breach: `429 rate-limited` (Problem Detail with `retry_after`) + `Retry-After`
header. Emit the IETF-draft **`RateLimit`** + **`RateLimit-Policy`** structured-field headers
(RFC 9651 syntax) so well-behaved clients self-throttle; optionally mirror legacy
`X-RateLimit-*`. **IPv6 nuance (ironic but real):** limit on the **/64 prefix**, not the
/128, so a single subscriber can't rotate addresses to evade, and NAT'd IPv4 users behind
CGNAT aren't over-throttled; keep limits generous — the endpoint is a public good. No
accounts needed: IP (and /64) is the partition. Encourage (don't require) a descriptive
`User-Agent` / optional `?sourceapp=` as the polite path for high-volume research clients
(RIPEstat precedent).

### 7.4 Compression

gzip + Brotli at the **nginx/CDN edge** for all JSON / CSV / SVG-text / Atom responses over
~256 bytes, with `Vary: Accept-Encoding` (Brotli preferred, gzip fallback). Let the edge
compress so the Go origin emits uncompressed bodies (simpler; origin sits behind
nginx+CDN). BREACH-class risk is a non-issue — responses are public data with no secrets or
tokens (anonymous API). Don't double-compress; the already-tiny SVG badge gains little.

## 8. OpenAPI-first workflow

**Decision.** A hand-authored **`openapi.yaml` (OpenAPI 3.0.3)** at the repo root is the
single source of truth; both sides generate from it, and CI blocks drift.

- **Version 3.0.3, not 3.1.** oapi-codegen *mainline* (the one with the chi-server +
  strict-server generators) does not yet support 3.1 (awaiting the libopenapi rewrite,
  still experimental). Since chi v5 is locked, oapi-codegen `chi-server` + `strict-server`
  is the natural spec-first Go path (thin, type-safe handlers that auto-marshal and set
  content-type/status). This API's payloads — the status/classification enums, aggregate
  percentages, cursor pagination, RFC 9457 errors — are **all expressible in 3.0.3** (using
  `nullable: true` for the `null` status values), so the 3.1 gap costs nothing.
- **Go side:** oapi-codegen generates server interface + types + request validation; handlers
  implement the strict interface. *Rejected — ogen* (native 3.1, no `reflect`/`interface{}`):
  it owns the router/server and would displace the locked chi v5 — a stack change, not a
  drop-in; only worth it if a true 3.1 document becomes non-negotiable.
- **Frontend side:** **openapi-typescript** (types, zero runtime deps) +
  **openapi-fetch** (tiny typed fetch wrapper) — the thin gold standard for a read-only,
  handful-of-endpoints public API, composing cleanly with Vue 3.5 + Pinia. The snake_case
  wire (§3.3) yields snake_case TS property names — non-idiomatic but fully type-safe.
  *Rejected — Orval/Hey-API/Kubb* (React-Query hooks, Zod, MSW mocks): batteries this API
  doesn't need yet; revisit only if the frontend later wants generated composables or
  runtime validation.
- **Drift gate:** `make generate` runs oapi-codegen (Go) + openapi-typescript (TS); CI
  regenerates and `git diff --exit-code`s to block staleness, and lints the spec with
  Spectral/vacuum (enforcing the snake_case rule, the `{items,page,meta}`/`{points,meta}`
  envelopes, and the `problem+json` error schema). The `manifest.json` schema (§6.3), the
  keyset cursor grammar, the RFC 9457 problem shapes, and the badge/feed representations are
  all in `components` so the gate covers them. This is the mechanism that makes "OpenAPI-first"
  real rather than aspirational — and the concrete deliverable the rebuilt frontend's data
  layer is co-designed against.
- **Discoverability:** serve `openapi.json` at a stable path with Redoc/Swagger UI;
  additionally publish an `llms.txt` docs index (Radar precedent). A read-only MCP server is
  a cheap later add. Do **not** copy Pulse's free-account+API-key gate — it violates the
  anonymous lock.

## 9. Data-history migration — the flagged open decision

The DNS-flip cutover means a fresh crawl is acceptable and the **mandatory** production data
migration is dropped. What remained was one genuine decision, now resolved.

**Decision (OPEN-9, 2026-07-09): start fresh — no history import now; revisit later.** Both
the `changelog` and the `scan` hypertable begin empty. The DNS-flip cutover carries **no data
import** at all: no structured changelog loader, no entity-resolution/orphan-create step, no
scan backfill. The changelog-sourced features (the diff / "who went green" #4, the change
feeds §6.4, the per-domain changelog §5.8, the reconstructed history trajectory §5.9, and the
"State of IPv6" report #6) launch empty and **fill over the months following launch** as the
fresh crawl accumulates confirmed transitions. The fresh-scan **latency overlay** on §5.9
likewise starts empty and fills over ~90 days. A best-effort structured changelog import
remains a possible **later** step if the empty-history gap proves painful, but it is not part
of round-1.

Because there is no import, the schema simplification is taken **unconditionally**: drop
`changelog.legacy_message`/`legacy_status` + the three `changelog_*_chk` CHECK constraints
(make `old_value`/`new_value` NOT NULL outright), drop `'legacy'` from the `changelog.field`
domain, and drop the `created_by = 'import'` enum value (no import means no orphan-created
import rows). See §10.3 (schema) and §10.4 (cutover), both collapsed to the pure DNS-flip.

The rejected alternative — a **best-effort structured changelog import** (native
`(domain_id, ts, field, old_value, new_value)` rows from the retained production dump, keyed
through 08 §3 entity resolution with an orphan-create step) — was the earlier recommendation:
it would have populated the credibility surface on day 1 rather than over months. It is set
aside for now (revisit later) to keep the cutover a clean, zero-import DNS flip; the raw
`scan` hypertable was always going to start fresh regardless.

### Tradeoff

| | Start fresh (**resolved**) | Best-effort structured import (deferred) |
|---|---|---|
| Day-1 changelog / diff / feeds / per-domain history trajectory / State-of-IPv6 | Empty; fills over months | Populated, credible |
| Day-1 §5.9 latency overlay | Empty | Empty regardless (scan starts fresh) |
| Effort | Zero | Low (structured loader + 08 §3 entity resolution) |
| Schema | Drop `legacy_*` **and** `'import'` | Drop `legacy_*`; keep `created_by='import'` (required) |
| Risk | None | Best-effort mapping may drop some rows (acceptable) |
